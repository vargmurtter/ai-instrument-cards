# AI-помощник для подготовки товарных описаний

Прототип по тестовому заданию: сервис принимает JSON с данными контрольно-измерительного прибора и возвращает черновик карточки товара для B2B-интернет-магазина. Генерация — модель `qwen3:4b` через Ollama, API — FastAPI.

Что отдаёт сервис:

- SEO-заголовок (до 70 символов);
- SEO-описание (800–1200 символов);
- структурированные характеристики — дословно из входных данных, отсутствующие помечены «данных нет»;
- 3–5 поисковых запросов;
- commercial-блок для менеджера;
- `missing_data` и `warnings` — чего не хватает во входных данных и где модель могла ошибиться.

## ⚠️ Модель тяжёлая — сначала проверьте железо

`qwen3:4b` — это ~2.5 ГБ весов и 4–6 ГБ оперативной памяти в работе. В Docker к этому добавляется образ `ollama/ollama` (~7 ГБ) и скачивание модели в `./ollama-models` при первом запуске.

Скорость генерации одной карточки (один-два прохода модели, если сработал ретрай):

| Железо | Время |
|---|---|
| GPU, удалённая Ollama | ~2–3 минуты |
| CPU в Docker на macOS, 8 ядер | ~5–8 минут |

Docker на macOS не имеет доступа к GPU, модель считает на CPU. Если железо слабое — используйте вариант 2 с удалённой Ollama.

## Вариант 1. Всё в Docker, одна команда — мощное железо

```bash
docker compose up -d --build
```

Что произойдёт: соберётся образ приложения, поднимется Ollama, при первом запуске скачается модель в `./ollama-models` (2.5 ГБ, несколько минут в зависимости от сети). Контейнер приложения стартует только после того, как модель появилась в Ollama — за это отвечает healthcheck.

Проверка:

```bash
docker compose ps
curl -s http://127.0.0.1:8000/health
```

Ожидаемый ответ:

```json
{"status":"ok","ollama":{"host":"http://ollama:11434","model":"qwen3:4b","reachable":true,"model_available":true,"models":["qwen3:4b"],"error":null}}
```

- Swagger: http://127.0.0.1:8000/docs
- Логи: `docker compose logs -f ollama`, `docker compose logs -f app`
- Остановить: `docker compose down` — модель остаётся в `./ollama-models`
- Удалить вместе с моделью: `docker compose down && rm -rf ollama-models`

На Linux с NVIDIA GPU Ollama в контейнере ускоряется одной строкой в сервисе `ollama`:

```yaml
    gpus: all
```

## Вариант 2. Только приложение, Ollama удалённо — слабое железо

Модель работает на отдельной машине, приложение — локально в venv.

1. На машине с Ollama нужна модель и доступ по сети (по умолчанию сервер слушает только localhost):

```bash
ollama pull qwen3:4b
OLLAMA_HOST=0.0.0.0:11434 ollama serve
curl http://<ip-машины>:11434/api/tags   # проверить доступность
```

2. Локально поставить зависимости:

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env      # если .env ещё нет
```

3. В `.env` прописать адрес удалённой Ollama:

```
OLLAMA_HOST=http://192.168.1.18:11434
MODEL=qwen3:4b
TIMEOUT=600
```

4. Запустить:

```bash
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Переменные окружения из шелла приоритетнее `.env`, поэтому можно разово переопределить:

```bash
OLLAMA_HOST=http://192.168.1.18:11434 .venv/bin/uvicorn app.main:app --port 8000
```

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `OLLAMA_HOST` | `http://localhost:11434` | адрес Ollama; в compose для контейнера переопределяется на `http://ollama:11434` |
| `MODEL` | `qwen3:4b` | имя модели |
| `TIMEOUT` | `600` | таймаут одного запроса к модели, секунды |

Файл `.env` в `.gitignore`; шаблон — `.env.example`.

## Проверка работы

Доступность сервиса и модели:

```bash
curl -s http://127.0.0.1:8000/health
```

Одна карточка:

```bash
curl -s http://127.0.0.1:8000/api/cards \
  -H 'Content-Type: application/json' \
  -d '{"name":"Манометр показывающий DM 02","manufacturer":"Манотомь","specs":{"диапазон измерений":"0–1,6 МПа","класс точности":"1,5","присоединение":"G1/2","диаметр корпуса":"100 мм"},"description":"Прибор предназначен для измерения избыточного давления неагрессивных к нержавеющей стали жидкостей и газов."}'
```

Два демо-товара сразу (данные лежат в `data/products.json`): первый — манометр DM 02 из примера ТЗ, второй — выдуманный датчик ПД-100 с неполными данными.

```bash
curl -s http://127.0.0.1:8000/api/cards/batch \
  -H 'Content-Type: application/json' \
  -d "{\"products\": $(cat data/products.json)}"
```

Проверка обработки ошибок:

```bash
# 422 — пустое название
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/api/cards \
  -H 'Content-Type: application/json' -d '{"name":"  ","manufacturer":"Манотомь"}'

# 422 — specs не объект
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/api/cards \
  -H 'Content-Type: application/json' -d '{"name":"Манометр","manufacturer":"Манотомь","specs":"строка"}'
```

Если Ollama недоступна, `POST /api/cards` вернёт `502`, при превышении таймаута — `504`. При этом `/health` отвечает `200` с `reachable: false`, чтобы можно было отличить проблему с моделью от падения сервиса.

## Промпты и принятые решения

**Текст пишет модель, характеристики — код.** Список характеристик собирается из входных данных программно: значения берутся дословно, отсутствующие получают «данных нет» и попадают в `missing_data`. Модель физически не может придумать характеристику, потому что она их не генерирует.

**Промпт: минимум свободы.** System-промпт задаёт жёсткие правила: единственный источник фактов — входной JSON; нельзя добавлять числа, единицы, сертификаты, гарантии; отдельно запрещены типовые выдумки — диапазон рабочих температур, степень защиты IP, срок службы; поля со значением «данных нет» в тексте не упоминаются. Дополнительно задана структура: заголовок 50–70 символов, описание 900–1150 символов тремя абзацами (назначение → конструкция → задачи и аудитория), 3–5 запросов, commercial-блок на два абзаца. В user-сообщение уходит компактный JSON товара и список отсутствующих полей.

**Структурированный вывод.** Схема ответа описана pydantic-моделью `CardDraft` и передаётся в Ollama параметром `format=CARD_SCHEMA`. Это включает constrained decoding: модель возвращает JSON по схеме, без markdown и ```-обёрток. Для `qwen3:4b` дополнительно отключены рассуждения (`think=False`) — иначе thinking уходит в отдельное поле, а `content` приходит пустым.

**Пост-проверки.** После генерации код проверяет длины (заголовок ≤70, описание 800–1200, запросов 3–5) и числа: каждое число из текста модели должно встречаться во входных данных (однозначные 0–9 разрешены как счётчики). При нарушении — один повторный запрос с перечислением конкретных проблем, затем принудительные правки: обрезка по границе слова или предложения с записью в `warnings`. Итоговый статус: `ok`, `completed_with_gaps` (есть пропуски в данных) или `needs_review` (есть предупреждения).

**Ошибки и конфиг.** Некорректный JSON и пустые обязательные поля — стандартный `422` FastAPI; недоступная Ollama — `502`, таймаут — `504`. Адрес, модель и таймаут вынесены в `.env`, ключей API нет — Ollama вызывается по HTTP внутри сети.

## Ограничения

- `qwen3:4b` — небольшая модель: качество текста неровное, иногда она всё же добавляет правдоподобные, но не подтверждённые формулировки без чисел (например, «не требует обслуживания») — такие места гвард не ловит.
- Числовой гвард — эвристика: однозначные числа пропускаются, поэтому выдуманная «точность 5» может проскочить.
- Если описание получилось короче 800 символов, оно не добивается автоматически — только помечается `description_too_short`.
- Пакетный режим обрабатывает товары последовательно: время растёт линейно, очереди и параллелизма нет.
- Нет аутентификации, кэша и сохранения результатов — это прототип, а не продакшен-сервис.
